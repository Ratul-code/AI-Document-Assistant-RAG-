## Recent addition: VPS deploy readiness — env templates tracked, prod config corrected

Ran a full deploy-readiness audit against the VPS workflow (`docker compose -f compose.yaml -f compose.prod.yaml -f compose.vps.yaml up -d --build`). The build system, migration chain, Caddy routing, and compose overlay layering all check out. Three deploy blockers were found and fixed.

- **Root `.env.example` is now tracked** — it was untracked, so `cp .env.example .env` (the first step of the documented VPS deploy, `DOCKER.md`) would have failed on a fresh clone with a confusing "file not found". The root `.env` template is the *deploy-time* config (`DOMAIN`, `NEXT_PUBLIC_API_BASE_URL`, `IMAGE_TAG`, `APP_ENV`) read by Compose for `${VAR}` interpolation — distinct from `backend/.env`, which holds the *application* secrets. That split is now documented in the template itself.
- **`Caddyfile` and `compose.vps.yaml` are now tracked** — both were untracked despite being required by the deploy command. `compose.vps.yaml` is the third overlay that re-enables local `build:` for the backend and frontend (because `compose.prod.yaml` clears it with `!reset null` in favour of a registry image that does not exist yet), and the `Caddyfile` is bind-mounted into the Caddy container at `/etc/caddy/Caddyfile`.
- **`backend/.env` set to production values** — it was still on dev settings, which the fail-fast validator in `app/core/config.py` rejects outright when `APP_ENV=prod` (`APP_DEBUG=true`, the default `JWT_SECRET`, `COOKIE_SECURE=false`, and localhost `CORS_ORIGINS`). Because the api, worker, and beat containers all import `get_settings()` at module load, all three would have crash-looped on boot — and `depends_on: {condition: service_healthy}` would have blocked worker and beat behind the failing api, taking the entire stack down. `APP_ENV=prod`, `APP_DEBUG=false`, a fresh 64-char `JWT_SECRET`, `COOKIE_SECURE=true`, `COOKIE_SAMESITE=lax`, and `CORS_ORIGINS` pointing at the public origin are now set.
- **Alembic pooler question resolved — no code change** — the config carried `DATABASE_URL_SYNC` (session pooler, port 5432) with a docstring calling it the "Sync URL for Alembic" and `backend/.env.example` asserting that DDL cannot run through the transaction pooler. Verified by direct test against the live Supabase project: `CREATE TYPE` **succeeds** through port 6543, three concurrent `pg_advisory_xact_lock` transactions serialize correctly, and the full 9-revision chain (including all four native Postgres ENUM types) applied cleanly from an empty database via the transaction pooler. The behaviour was therefore already correct; only the **comments were wrong**. `backend/alembic/env.py`, the `database_url_sync` field description in `app/core/config.py`, and `backend/.env.example` now state which URL Alembic actually uses, record the verification, and document the fallback plan if a future pooler release ever restricts DDL.
- **Test harness hardened against a production `.env`** — `backend/.env` now carries production values (`APP_ENV=prod`, `COOKIE_SECURE=true`), and the test suite inherited them, which broke 15 tests with `401 "Not authenticated"`. Two separate causes, both fixed in `backend/tests/conftest.py`: the `APP_ENV` pin now stops the prod fail-fast validator from firing during tests, and `COOKIE_SECURE` is pinned to `false` because the `TestClient` speaks plain HTTP and a `Secure` cookie is never sent back over it. Both pins are set at **module scope, before the app is imported** — not inside the autouse fixture — because `app/api/v1/endpoints/auth.py` snapshots `_settings = get_settings()` at import time and reads `_settings.cookie_secure` when setting the auth cookies. A per-test fixture runs too late: the module has already frozen the value. This was the non-obvious part; the failure surfaced as a generic 401 with no mention of cookies or env.
- **Verification** — `pytest tests/core/ tests/api/` — 3 pre-existing failures remain in `tests/api/test_rate_limit.py` (`redis.exceptions.ConnectionError`: `redis://redis:6379/2` is the Docker-internal hostname, which does not resolve when the suite runs on the host). Confirmed pre-existing by re-running the same three tests against the original dev `.env` — they fail identically. They are unrelated to this change and need a reachable Redis.
- **`Settings()` under `APP_ENV=prod` validates with no errors and no warnings. `app.main` imports cleanly (34 routes). `alembic/env.py` parses. `docker compose -f compose.yaml -f compose.prod.yaml -f compose.vps.yaml config` resolves with `NEXT_PUBLIC_API_BASE_URL=https://yourdomain.com` and `DOMAIN=yourdomain.com`, and publishes only Caddy's 80/443 — the api and frontend host ports are correctly stripped by `compose.prod.yaml`.**
- **Remaining manual steps on the VPS** — set `DOMAIN` + `NEXT_PUBLIC_API_BASE_URL` in the root `.env`; create the private `doc-uploads` bucket in Supabase (the client never calls `create_bucket`); open ports 80/443/UDP-443 for the ACME HTTP-01 challenge; confirm the DNS A record points at the VPS.


## Recent addition: Rate limiting via `slowapi`

Added per-route HTTP rate limiting to the FastAPI backend using the `slowapi` library (the de-facto FastAPI port of `flask-limiter`). The limiter is wired into `create_app()`, all 25 user-facing routes are decorated with `@limiter.limit(...)`, and a custom JSON `RateLimitExceeded` handler returns HTTP 429 with the same `{"detail": "..."}` shape the rest of the API uses.

- **Single source of truth — `app/core/rate_limit.py`** — holds the module-level `Limiter` instance, the `user_or_ip_key(request)` keying function, and the `_rate_limit_exceeded_handler`. Per-route limits are documented inline in its module docstring (the table is the contract).
- **Keying policy** — `user_or_ip_key` decodes the access-token cookie when present and returns `user:<uuid>`; otherwise it falls back to `ip:<remote-address>`. Pre-auth routes (`/auth/*`) are IP-keyed so brute-force is bounded; post-auth routes are user-keyed so two users behind the same NAT don't share a bucket.
- **Storage — Redis DB 2** — separate from Celery's DB 0 and WS pub/sub's DB 1 (`RATE_LIMIT_STORAGE_URI=redis://localhost:6379/2`). A `FLUSHDB` on either of the other DBs now leaves rate counters untouched. `memory://` is also supported via env override.
- **Per-route limits** — `5/hour` on `POST /auth/register`, `5/minute` on `POST /auth/login` (brute-force mitigation), `30/minute` on `POST /auth/refresh`, `10/minute` on `POST /auth/logout`, `60/minute` on `GET /auth/me`. Documents: `10/minute` `upload-intent` (signed URL + DB row, expensive), `30/minute` `confirm` / `upload-failed` / `DELETE`, `60/minute` PATCH / downloads / views / stats / logs, `120/minute` list. Analysis: `20/minute` on both `/analysis/query` and `/analysis/query/stream` (LLM cost exposure). Conversations: `60/minute` POST / GET by id / PATCH / DELETE; `120/minute` sidebar list / messages list; `30/minute` `submit_message` and `cancel_message`. **Unlimited**: `/health/*` (LB/k8s probes) and `/ws` (slowapi is HTTP-only).
- **Two new settings** — `RATE_LIMIT_ENABLED` (default `true`, master switch — flip off in test suites that hit an endpoint >N times) and `RATE_LIMIT_STORAGE_URI` (default `redis://localhost:6379/2`). Both added to `backend/app/core/config.py` and documented in `backend/.env.example`.
- **`from __future__ import annotations` dropped in 4 endpoint files** — `auth.py`, `documents.py`, `analysis.py`, `conversations.py`. Reason: the future import stringifies parameter annotations; slowapi's `@limiter.limit(...)` wraps the handler; FastAPI's `lenient_issubclass` (which detects the `Request` / `Response` special params) requires real class objects, not strings. Without the fix, every rate-limited route 422s because `payload` is treated as a query param. The drop is documented in a comment at the top of each affected file.
- **`Response` parameter added to handlers that return Pydantic** — slowapi's auto-header injection needs a `Response` object to stamp `X-RateLimit-*` headers onto. Any handler that previously returned a Pydantic model (rather than a `Response`) now takes `response: Response` as a keyword arg — FastAPI injects it automatically, slowapi picks it up via `kwargs.get("response")`.
- **Test suite** — new `backend/tests/api/test_rate_limit.py` with 5 tests: login throttle (6th request 429s), health not throttled (200 hits stay 200), master switch off (100 logins never 429), per-user keying (two users each get their own bucket), 429 response shape (JSON body with `detail` key + `Retry-After` header). All 5 pass; the rest of the API suite (42 pre-existing tests) still passes.
- **Conftest default** — `tests/conftest.py` now sets `RATE_LIMIT_ENABLED=false` for every test by default and also flips `limiter.enabled = False` on the singleton (slowapi reads the attribute, not the env var). The dedicated rate-limit test re-enables the limiter via a per-module fixture that calls `limiter.reset()` between cases.
- **No frontend changes** — the frontend already handles 429 as a non-200 response; no toast / error-branch work needed.
- **No contract change** — every response shape, DB schema, WS event, and model field is unchanged. New env vars are additive (both have non-empty defaults).
- **Verification** — `pytest tests/api/` clean (47/47). `pytest tests/` — 7 pre-existing failures in `tests/tasks/` and `tests/tasks/test_embedding_logs.py` are unrelated to this change (missing enum values, `AsyncEngine` setup) and predate it.

## Recent addition: Docker + docker-compose for the backend stack

Containerised the backend so the project can ship to a VPS as a self-contained unit. Frontend is intentionally left out for now — it runs with plain Node on the host. See `DOCKER.md` at the repo root for the operator cheat sheet.

- **`Dockerfile`** (multi-stage, repo root) — `python:3.12-slim` builder installs deps into `/opt/venv` with build tools, then a slim runtime stage copies the venv + source only. Final image has no compilers, runs as non-root `app` user, uses `tini` for proper signal handling. Default `CMD ["api"]`; worker/beat override via compose.
- **`docker-entrypoint.sh`** (`backend/`) — single dispatcher that translates the short CMD keyword (`api` / `worker` / `beat`) into the real uvicorn / celery command. Before handing off it (a) waits up to 60s for Postgres to be reachable, (b) runs `alembic upgrade head` so the schema is always current, then (c) `exec`s the real process so it becomes a child of tini and receives signals.
- **`docker-compose.yml`** (repo root) — five services: `api`, `worker`, `beat`, `redis` (`redis:7-alpine`, healthcheck + persisted `redis_data` volume), `postgres` (`postgres:16-alpine`, behind the `local-pg` profile so it stays off until asked). All three app services share the same image. Named volumes: `redis_data`, `hf_cache` (so the ~1.2GB sentence-transformers model download persists), `postgres_data`. The compose file reads `backend/.env` for secrets and overrides only the Celery URLs to point at the in-container redis (`redis://redis:6379/0`). `depends_on: condition: service_healthy` on every link.
- **`.dockerignore`** (repo root) — excludes `.venv`, `__pycache__`, `.git`, `node_modules`, `frontend/`, all `.env` files except `.env.example`, local `*.db` files, tests, eval, etc. Keeps the build context small and prevents secret leakage.
- **`DOCKER.md`** (repo root) — operator-facing cheat sheet: TL;DR commands, file map, how the one-image-three-jobs pattern works, env var sources, common operations, VPS deployment steps, troubleshooting.
- **`.env` strategy** — the existing `backend/.env` is reused as-is by compose (`env_file:`); only the broker URL is overridden. Zero code changes in `backend/app/**`. The non-Docker dev workflow is unaffected.
- **Verification** — `docker compose config` validates the file as syntactically correct and shows the resolved env (DATABASE_URL points to Supabase, CELERY_BROKER_URL points at the in-container redis, all LLM/Supabase keys load from `backend/.env`). No `docker compose up` was run — that requires Docker Desktop installed locally and would take 5–10 min on first build.
- **No contract change.** No API endpoint, DB schema, WS event, or model field touched.
- **No `docs/decisions.md` change** — the architectural call (dockerise backend only, reuse existing `.env`, single shared image) is documented inline in `DOCKER.md` and is more operational than architectural. If/when a VPS deployment ADR is needed, it can be added as ADR-020.

## Recent addition: progress bar always visible, one log row per stage

The activity log was emitting a row per page during chunking (and per batch during embedding), and the progress section in the detail dialog disappeared the moment a doc reached `ready` or `failed` — so opening the dialog for an already-processed doc left no progress context at all. This change reduces the log to one row per stage and makes the progress bar a permanent fixture of the dialog.

- **Per-page chunking logs removed** (`backend/app/tasks/document.py`, `_chunk_pages_for_document`) — the inner loop no longer writes a `chunking.progress` row per page. It still publishes the `document.embedding_progress` WS event per page so the UI bar keeps advancing, and the caller still emits the single terminal `chunking` row at the end.
- **Per-batch embedding logs removed** (`backend/app/tasks/embedding.py`, `_process_one_document`) — the per-batch `embedding.progress` log row is gone. The terminal `embedding` / `embedding_failed` row stays, decided by the same `succeeded` / `failed` counts the doc-level status flip uses.
- **All intermediate breadcrumbs erased** (`backend/app/tasks/document.py`, `backend/app/tasks/embedding.py`, `backend/app/api/v1/endpoints/documents.py`, `backend/app/models/document_log.py`) — the per-doc activity feed now contains exactly **one row per stage** plus at most one failure row, no more. The previous emission pattern wrote 9–11 rows per doc including `download.started/completed`, `parse.started`, `chunking.started`, `embedding.started`, `upload.received`, `upload.confirmed`, and lifecycle `ready`/`failed` rows that just repeated what the stage row already said. Those are all gone. The complete log surface after this change is **9 event types**: `uploaded`, `parsing`, `chunking`, `embedding`, plus `parsing_failed`, `chunking_failed`, `embedding_failed`, `processing_failed` (catch-all), and `document.deleted`. The per-doc feed reads as `uploaded → parsing → chunking → embedding`, one row each. Backend enum (`DocumentLogEventType`) now lists only those 9 values; the frontend type union mirrors them.
- **Catch-all failure handler** (`backend/app/tasks/document.py`, `_mark_stage_failed`) — when an unexpected exception in `process_document` blows up at an unknown stage, we flip the doc to FAILED and write a `processing_failed` activity-feed row instead of the generic `failed` lifecycle row. The `embedding` worker still writes `embedding_failed` directly when all batches fail.
- **`_mark_failed` no longer writes its own log row** — it now only flips the status + pushes the WS `document.status` event. The activity-feed failure row is written separately by the caller using a stage-specific event_type, so the feed doesn't double up.
- **Progress bar is now always visible** (`frontend/src/components/documents/document-progress-stepper.tsx`, `document-detail-dialog.tsx`) — the section is no longer hidden on terminal `ready` / `failed`. The stepper renders a single shadcn `Progress` bar driven by the live `document.embedding_progress` WS tick; when no live tick is in memory (the user just opened the dialog for a doc that was processed before they connected), it falls back to `stats.chunks_embedded / stats.chunks_total` so the bar still shows a meaningful, filled value. Status icon (spinner / check / x) + phase label on the left, live counter on the right, model name + failed count + percent in the subtitle.
- **Stats passed to stepper as fallback** — `DocumentProgressStepper` now takes a `stats?: DocumentStatsResponse` prop. Live WS data still wins when present; the stats payload is the safety net for fresh-opened dialogs and for any time the in-memory WS cache hasn't seen the doc yet.
- **Frontend `humanizeLogType` updated** (`frontend/src/components/documents/document-log-row.tsx`, `frontend/src/lib/api/documents.ts`) — the table now has exactly 9 entries matching the 9 backend event types. Each `*_failed` row gets a destructive-red surface + the stage's icon so the outcome reads immediately. Old entries (`upload.received`, `chunking.progress`, `embedding.started`, …) removed.
- **Note on stale rows**: docs that were processed BEFORE this change still have the old per-page / per-batch rows in `document_logs`. To verify the new behaviour, upload a fresh document. A one-off cleanup migration is intentionally NOT included — historical rows represent an honest timeline of an older doc, and they're what the previous code did.
- **Verification**: `npm run lint` clean (3 pre-existing warnings in unrelated files), `npx tsc --noEmit` clean, `npm run build` clean, `ast.parse` clean on all 4 modified backend files.
- **Docs**: no `docs/DESIGN.md` change — same semantic tokens (lime brand for the active progress fill, destructive for the failed-count subtitle and the `*_failed` surface).
- **No contract change.** WS event family, REST endpoints, `DocumentLog` model, and `document.embedding_progress` payload are unchanged. The log feed simply gets fewer rows now (one per stage instead of N per page/batch).
- **Verification**: `npm run lint` clean, `npx tsc --noEmit` clean, `npm run build` clean, `ast.parse` clean on both modified backend files.
- **Docs**: no `docs/DESIGN.md` change — same semantic tokens (lime brand for the active progress fill, destructive for the failed-count subtitle and the `failed` border tone). No new component variants.


## Recent addition: simplify document scope picker (implicit "all documents")

The chat app's document scope picker used to render an "All documents" checkbox as a separate row at the top of the dialog, with a globe icon and a description. The row was redundant — "all documents" is exactly the state where the user has picked nothing — and the dialog's primary button said "Start chat" in create-mode but "Save" in edit-mode, a small inconsistency that confused the flow. The user requested the change explicitly. See ADR-024.

- **Removed the "All documents" row** (`frontend/src/components/chat/document-scope-picker.tsx`). The picker body now shows only the ready-doc list with tick checkboxes plus the "Select all" / "Clear" helper pair. The "Or pick specific documents" section header becomes just "Documents" (no "or" — there's no sibling toggle). The list is no longer greyed out behind an "all" mode. The `Globe2` lucide import drops.
- **"All documents" is the implicit default.** No ticks selected → scope is every ready document. The wire convention `{ scope_all_documents: true, document_ids: [] } = all documents` is preserved; the three payload sites (the dialog's POST, the dialog's PATCH, and the welcome screen's own create-mutation) all derive `isAll` from `documentIds.length === 0` so they agree.
- **`describeScope` reads `documentIds.length === 0` as "all".** The legacy `allDocuments` flag on `DocumentScope` is kept on the type for stability but is no longer the source of truth. `sameScope` in the dialog compares arrays only. The picker body always emits `allDocuments: false`.
- **Live pill mapping in `ChatWelcome`** (`frontend/src/components/chat/chat-welcome.tsx`). The welcome screen derives a `displayScope` whose `allDocuments` mirrors `documentIds.length === 0` and feeds it into `describeScope` and the composer placeholder, so the user sees "All documents" while they have no ticks selected — matching the saved state. The previously-unreachable `composerHint` ("Pick at least one document above…") is removed; the welcome's `Composer` hint is the default `"Press ⌘+Enter to send."` always.
- **Dialog primary button label is "Save" in both modes** (`frontend/src/components/chat/document-picker-dialog.tsx`). The previous `"Start chat"` ternary collapses to a constant. The create-mode can-save guard `!allDocuments && documentIds.length > 0` is removed — any state is saveable in create-mode because "all documents" is a valid explicit choice. Edit-mode keeps the `!sameScope` guard so a no-op PATCH doesn't fire.
- **Picker no longer strands empty chats in the welcome flow** (`frontend/src/components/chat/document-picker-dialog.tsx`, `frontend/src/components/chat/chat-welcome.tsx`). Pre-fix, the dialog's create-mode fired `POST /conversations` on every Save click but the welcome never passed `onCreated`, so each click created an "Untitled chat" in the sidebar while the UI stayed on the welcome screen. New `onConfirm?: (scope) => void` prop on the dialog: when provided in create-mode, the dialog hands the current scope to the parent and closes without creating. `ChatWelcome` passes a no-op `onConfirm` (the scope is already kept in sync via `onScopeChange`) so the picker's Save just commits the scope and closes. The actual conversation is only created when the user sends the first question via the composer (the existing `createAndOpen` mutation in `ChatWelcome`). Edit-mode (chat header) is unchanged.
- **No contract change.** Wire payload for `POST /conversations` and `PATCH /conversations/{id}` is unchanged. `Conversation` model in the backend is unchanged. Persisted chats from before this change still render correctly in the chat header pill and the workspace composer hint.
- **No `DESIGN.md` change.** The visual migration charter in `docs/DESIGN.md` §1 normally forbids behavior changes; this is an explicit, user-authorized exception recorded in ADR-024. No design tokens change.
- **Verification**: `npm run lint` clean, `npx tsc --noEmit` clean, `npm run build` clean.

## Recent addition: real-time numbers, logs, and progress on the Documents page

The detail dialog's "Progress" section used to only update if the dialog was open before the worker fired its first `document.embedding_progress` event — and the four stat tiles (Pages / Chunks / Embedded / Status) were a stale REST snapshot, never refetched after the first paint. The cross-doc "Activity" feed didn't subscribe to WS pushes at all, so new log lines only showed up on the next mount or a manual "Load more". This change wires every UI surface that should react to worker activity — the page-level live strip, the doc list, the detail dialog's stats, the per-doc Logs panel, and the cross-doc Activity feed — to the same WS family the backend already publishes (`document.status`, `document.log`, `document.embedding_progress`).

- **Live progress strip on `/documents`** (`frontend/src/components/documents/live-progress-strip.tsx`) — a sticky card at the top of the page (renders nothing when no doc is in flight). One row per in-flight doc (`status ∈ {processing, uploaded, learning}`) showing title, the 4-dot pipeline stepper (Uploaded → Parsing → Chunking → Embedding), the live shadcn `Progress` bar (`<chunks_done> / <chunks_total>`), the latest log message (e.g. "Page 3/12 chunked", "Embedded batch 4 (200/380 chunks, 2 failed)"), the model name, and a live percentage. When the doc lands on `ready` or `failed`, the status bridge refetches the list, the row drops out of the in-flight filter, and the row disappears. Uses `bg-card/95 backdrop-blur` + `shadow-sm` so the strip stays legible while scrolling.
- **Page-level in-flight progress aggregator** (`frontend/src/lib/realtime/use-all-in-flight-progress.ts`) — a new hook that subscribes once to both `document.embedding_progress` (counters) and `document.log` (latest human-readable message) and returns a `Map<docId, InFlightProgress>`. Used by the strip so a single WS handler covers every in-flight doc, instead of N independent `useDocumentEmbeddingProgress` hooks each registering their own. Tick updates are O(1) `Map.set` per event; the map reference is stable across renders when there are no events so memoized consumers don't churn.
- **Log bridge now invalidates everything derived** (`frontend/src/lib/realtime/use-document-log-bridge.ts`) — on every `document.log` event the bridge now invalidates `documentKeys.lists()` (doc list refetches → row status pill / order updates), `documentKeys.stats(id)` (detail dialog's 4 stat tiles refetch from the DB), and the per-doc log page (already patched in place). This is the "every number updates in real time" trigger: a single log event from the worker causes the doc list, the dialog's stat tiles, and the per-doc log feed to converge to the latest DB state.
- **Status bridge now invalidates per-doc stats** (`frontend/src/lib/realtime/use-document-status-bridge.ts`) — previously only `documentKeys.lists()` was invalidated. Now also `documentKeys.stats(id)` and `documentKeys.detail(id)` on every `document.status`, so a transition like `LEARNING → READY` refetches the stats payload that the dialog reads its `status` from. Without this the dialog's "Progress" section could stay open for a tick after the worker flipped the doc to terminal.
- **Global cross-doc log bridge** (`frontend/src/lib/realtime/use-global-log-bridge.ts`) — new hook, mounted at app root via `RealtimeBridge`. Listens to `document.log` events and prepends the new row into any cache entry under `documentKeys.logs()` whose terminal key segment is an object (the `{limit, offset}` params used by `useMyLogs`) — per-doc log entries (where the terminal segment is a string documentId) are explicitly excluded so the two bridges don't double-write. Replay-safe (dedupes by item id). The cross-doc "Activity" feed now streams new rows in real time, the same way the per-doc panel already did.
- **Dialog "Progress" section is gated** (`frontend/src/components/documents/document-detail-dialog.tsx`) — the whole section is now hidden when the doc's `status` is `ready` or `failed`. The `DocumentProgressStepper` already rendered a small "Ready" / "Failed" chip on its own, so removing the section cleans up the dialog once the doc settles — the lifetime Logs panel below it shows the full event history. The `liveStatus` derivation prefers the WS-refetched stats payload and falls back to the doc snapshot, so the section disappears the moment the stats refetch lands after the status event.
- **No backend change.** All three event types (`document.status`, `document.log`, `document.embedding_progress`) are already published by `process_document` and `embed_chunks_for_document` and already persisted in the `document_logs` table. The log row remains the source of truth; the new page-level strip is a *consumer* of the existing event family.
- **No new dependencies.** Reuses the existing shadcn `Progress` primitive and Lucide icons. No new shadcn components required.
- **Verification**: `npm run lint` clean (the one pre-existing `use-upload-document.ts` warning is unrelated), `npm run build` clean — `/documents` continues to server-render on demand.
- **Docs**: no `docs/DESIGN.md` change — only documented tokens are used (semantic backgrounds, lime brand for the progress bar and active dot, destructive for failed counts). The sticky strip uses `bg-card/95 backdrop-blur shadow-sm` to stay legible on scroll; the design system permits shadows for elevated elements per §8.

## Recent addition: Logs panel + progress stepper in document detail dialog

The detail dialog's old 5-row "Recent activity" strip — a hybrid of REST snapshot + synthetic `document.status` events, capped at 5, rendered with its own ad-hoc row — is gone. In its place the dialog now has a **full lifetime Logs panel** (paginated, owner-scoped, real `document.log` rows from the existing `useDocumentLogBridge`) and a **live progress stepper** driven by the new `document.embedding_progress` WS event. Frontend-only; no backend changes, no contract changes.

- **Live progress stepper** (`frontend/src/components/documents/document-progress-stepper.tsx`) — a small card with 4 dots (`Uploaded · Parsing · Chunking · Embedding`), a shadcn `Progress` bar, and a one-line subtitle (`<chunks_done> / <chunks_total> chunks · <model_name>`, with `<failed_total> failed` appended in `text-destructive` when non-zero). ## Recent addition: WebSocket direct cross-origin with `SameSite=None; Secure` cookies

The FastAPI `/ws` endpoint was rejecting every upgrade with `ws rejected: no/invalid access_token cookie` because the browser does not attach the `xs` HttpOnly cookie on a cross-origin WebSocket handshake (`ws://localhost:3000` → `ws://localhost:8000`). The cookie is bound to `:8000` and the default `SameSite=Lax` blocks it from crossing origins for the WS upgrade specifically.

- **First fix (now superseded).** Added a `/api/ws` rewrite in `next.config.ts` and pointed the store at the same-origin path. Worked in `next dev` only — the production `next start` server's `handleUpgrade` is a documented no-op, so the rewrite would silently do nothing in production.
- **Final fix.** Removed the rewrite. `ws-store.ts` `wsUrl()` now connects directly to `${API_BASE_URL}/ws` (the FastAPI host). The backend sets the auth cookies with `SameSite=None; Secure` in production, which is what the browser requires to attach them to a cross-origin upgrade. HTTPS is mandatory in production for the `Secure` flag to be honored.
- **Local dev override.** `Secure` cookies are dropped over plain HTTP, so `backend/.env.example` documents the dev override (`COOKIE_SECURE=false; COOKIE_SAMESITE=lax`) and the frontend `.env.example` calls out the same caveat. The two configs must be kept in sync per environment.
- **No new dependency, no custom server.** The frontend's WS code, the backend's cookie code, and the existing CORS allowlist are unchanged in shape — only the cookie attributes and the store's `wsUrl()` moved.
- **Verification**: `npm run lint` clean, `tsc --noEmit` clean, `npm run build` clean.
- **Docs**: the cross-origin decision was rolled into the WS ADR (the one written for the same-origin rewrite, now describes the direct cross-origin path). `ADR-023` (added later) covers the separate document download & inline-view work.

## Recent addition: conversational query rewriting for retrieval (ADR-021)

After ADR-020 added chat history to the LLM prompt, follow-up questions like "what about the second one you mentioned?" still retrieved poorly — the dense embedder and the BM25 leg both see the raw current question, which is a bag of pronouns that matches nothing in the documents. The answer generator had context, but the retriever didn't. Fix: a tiny rewrite step that turns the chat-aware question into a self-contained, decontextualised query, fed only to the retriever (and the cross-encoder reranker, which gets a free improvement).

- **New module** `backend/app/services/document/analyser/query_rewrite.py` — pure async function `rewrite_query_for_retrieval(history, question, *, llm_provider, max_history_turns) -> str`. Fail-soft: empty history → no LLM call, returns question; provider raises → returns question; empty/whitespace response → returns question; the helper never raises. Strips accidental wrappers (quotes, "Rewritten query:" prefix, backticks). Tested with a hand-rolled fake provider, no network.
- **Parallel execution** in `app/services/document/analyser/__init__.py`: `analyse_query` now fires the rewrite task via `asyncio.create_task` *concurrently* with the candidate fetch (`asyncio.to_thread(run_in_sync_session, fetch_candidate_rows, ...)`). The wall-clock cap is `analysis_query_rewrite_timeout_s` (default 2.0s) enforced via `asyncio.wait_for` after both resolve. In the steady state the rewrite and the candidate fetch finish around the same time, so the rewrite is essentially free in latency. On timeout the orchestrator logs a warning and falls back to the raw question.
- **The retriever now sees the rewritten string**: `model.embed(query_text)` instead of `model.embed(question)`, and `query_text=query_text` for the BM25 leg in hybrid mode. The cross-encoder reranker (when enabled) also receives `query_text` — `(query, doc)` is the exact input shape it expects, so the rewrite is a free upgrade for rerank too.
- **The answer prompt is unchanged**: `build_messages(history=history, question=question, ...)` still gets the raw history and raw question so the model can answer naturally with pronouns. The rewrite is *only* for the retriever.
- **Separate, cheaper LLM** — `app/services/ai/llm.py` gets a new `get_rewrite_llm_provider()` factory. Same `OpenAICompatibleProvider` class, but reads from `analysis_query_rewrite_*` settings so operators can point the rewrite at a cheaper model (e.g. Gemini Flash-Lite via OpenRouter) without touching the answer-gen config. The provider's `__init__` gained an `api_key_env` kwarg so the rewrite can use a separate API-key env var if desired.
- **Settings** (in `app/core/config.py`, new section):
  - `ANALYSIS_QUERY_REWRITE_ENABLED` (default `true`) — master switch.
  - `ANALYSIS_QUERY_REWRITE_MAX_HISTORY_TURNS` (default `4`, range 0–20) — pairs sent to the rewrite. Smaller than the answer-prompt's 10 because the rewrite only needs enough context to resolve pronouns.
  - `ANALYSIS_QUERY_REWRITE_TIMEOUT_S` (default `2.0`, range 0.1–30.0) — hard wall-clock cap.
  - `ANALYSIS_QUERY_REWRITE_BASE_URL` (default `https://openrouter.ai/api/v1`) — gateway base URL.
  - `ANALYSIS_QUERY_REWRITE_MODEL` — exact OpenRouter slug. The default is a **placeholder**; the operator must set this in `.env` to the live slug for their chosen model (check `https://openrouter.ai/models`).
  - `ANALYSIS_QUERY_REWRITE_MAX_ASSISTANT_TOKENS` (default `80`), `TEMPERATURE` (default `0.1`), `API_KEY_ENV` (default reuses `ANALYSIS_LLM_API_KEY`), `HTTP_REFERER`, `X_TITLE`.

## Recent addition: model preload in the FastAPI lifespan (first request is fast)

The FastAPI process now warms the embedding-model and reranker singletons inside the `lifespan` startup handler so the first `/analysis/query` request doesn't pay the multi-second torch / checkpoint load cost. Both factories are already process-cached (ADR-019 + the MPS memory-leak fix in `progress.md`) — this change is just about moving the cache-fill from "request N=1" to "process startup".

- **Where**: `backend/app/main.py` — `lifespan(...)`. Imports `get_default_embedding_model` and `get_default_reranker` and calls both, in that order, before starting the WS subscriber.
- **Order matters**: the embedder is warmed first because every `/analysis/query` request needs it; the reranker is warmed only when `settings.analysis_rerank_enabled` is true, mirroring the orchestrator's own gate. This means an operator who flips `ANALYSIS_RERANK_ENABLED=true` after a restart pays exactly one model load at the next restart, not on the first user request.
- **Failure policy**: each preload is wrapped in `try / except Exception`. The factories themselves already fall back to `DeterministicStubModel` / `NoneReranker` on construction failure (the "loud one-shot warning" pattern from ADR-019), but the lifespan adds an outer guard for any unexpected raise (e.g. import-time failure, OOM during weight load). On failure the warning is logged and startup continues — a missing model never blocks the API from booting, so health checks and the docs surface stay reachable while ops investigates.
- **Logging**: each preload logs `embedding model preloaded: <name> (dim=<n>) in <s>s` / `reranker preloaded: <name> in <s>s` at INFO. The wall-clock timing surfaces in startup logs so an operator can see how much of the boot budget went to model prep. Both use `time.monotonic`.
- **Tests**: new `tests/test_lifespan_preload.py` (4 tests, all passing) drives the lifespan directly via `app.router.lifespan_context` and pins three things — the embedding factory is called exactly once during startup regardless of the rerank switch; the reranker factory is called once when `analysis_rerank_enabled=True` and **not at all** when false; a preload raise is contained and logged. Existing 282 backend tests still pass; the 5 pre-existing `tests/tasks/test_sweep.py` failures are unrelated (engine type mismatch in the sweep test fixture).
- **No settings change.** The preload reuses the existing `analysis_rerank_enabled` flag — there's no new env var. Operators who want to skip preload on a hot-reload dev loop can still flip the switch off and the embedder alone will warm.

## Recent addition: Doc2Dial as a second retrieval-eval corpus (with question-first capping)

The `backend/eval/` package now supports Doc2Dial as the retrieval-eval corpus. Doc2Dial is a multi-turn dialogue corpus grounded on user-facing documents (DMV / SSA / VA / StudentAid, 488 docs, 30,653 user turns across train/val/test). The dataset has its **own** `owner_id` and a **separate** persisted corpus at `eval/.cache/doc2dial/corpus.db` so `owner_wide` retrieval is isolated from any dev-DB state.

- **Loader** (`eval/scripts/doc2dial_loader.py`): downloads the official `doc2dial_v1.0.1.zip` release to `eval/.cache/doc2dial/`. Spans are embedded inside each `doc2dial_doc.json` document body (no separate span file). Doc ids are namespaced by domain; the loader emits `doc_key = "<domain>::<doc_id>"` as the global key. The loader's `load_dialogue_turns` is sorted by `(split, dial_id, turn_id)` so all downstream code agrees on canonical turn order. The new `cap_by_turns` helper applies the question cap: it slices the first N turns in canonical order, derives the doc set, and returns the kept docs + kept turns. There is no longer a popularity cap — that was the bug.
- **Capping** is now **question-first**: `--max-questions N` (default 40) on `ingest_corpus.py` and `build_dataset.py`. The seeder derives the doc set from the first N turns and ingests exactly those docs. `build_dataset` filters the corpus to the same doc set so every scored question's source doc is present. The manifest records `question_count` so the runner can confirm corpus and dataset agree.
- **Mapping** uses the LCS-overlap ≥ 0.5 fuzzy heuristic. Doc2Dial's evidence spans are short and chunk texts are doc-sized for the small docs, so the mapping usually succeeds once the doc is in the corpus. Verified: `--max-questions 40` produces **40/40 mapped to ≥1 chunk** (mapping floor 100% for the smoke slice).
- **Runner** (`eval/scripts/run_retrieval_eval.py`) now excludes rows with empty `relevant_ids` from the metric average. Recall and MRR are averaged over mappable questions only; `questions_total` and `questions_scored` are both reported in the JSON (plus an explicit `empty_gold_skipped` field) so the user can see whether a low score is a retriever problem or a mapping problem. Without this, an 8% mapping rate on a 30k question dataset would collapse the average to ~0 even when the retriever is fine.
- **CLI reference** (`backend/eval/CLI_REFERENCE.md`): new file with copy-paste cheatsheets for all four scripts × both datasets × both scope modes × both retrieval modes.

### Critical fix shipped with this change: question-first doc set derivation

The first Doc2Dial smoke run (`--max-questions 40`) reported `relevant_ids: []` for **every** question, all recall=0.0. Two compounding bugs surfaced:

1. **Doc-first cap was dropping the question's source doc.** The original `cap_documents` picked the top 20 docs by turn-count across the full 488-doc dataset, then kept only the turns that referenced those docs. A question's `doc_key` could easily be outside the top-20, in which case the seeder had no chunks for that doc, `build_question_row_doc2dial` silently set `scope_document_ids=[]` / `relevant_chunk_keys=[]`, and the runner reported 0.0 recall for what looked like a retrieval failure. The user spotted this and proposed the question-first approach.
2. **`cap_by_turns` and `load_dialogue_turns` sorted by different keys.** Even after switching to question-first, the seeder's "first 40 turns" (sort by `(dial_id, turn_id)`) and the build_dataset's "first 40 turns" (after the new `(split, dial_id, turn_id)` sort) picked different turns → the seeder ingested docs that the build step never asked about → 3/6 of the corpus's docs had no in-corpus questions, and the chunk-lookup filter returned 0 rows for half the question slice. Fix: `cap_by_turns` now uses the same `(split, dial_id, turn_id)` sort key as `load_dialogue_turns`. Both sides agree on what "first 40 turns" means; the corpus and the dataset stay in lockstep.

Final state of the smoke run: 6 docs / 13 chunks / 40 turns / **40/40 mapped** / single owner_id / single persisted DB. The user can now run the real embedder to get a Doc2Dial baseline.

## Recent fix: assistant answer vanishing on cross-route navigation

Submitting a question, navigating away from `/chat` mid-stream, and returning once the orchestrator had finished left the chat with no assistant bubble — only a hard refresh would show the persisted answer. The cause was structural: the `analysis.done` / `analysis.error` WS handler lived inside `ChatWorkspace`'s `useEffect`, so navigating to `/documents` (or any other route) unsubscribed the handler mid-stream. When the orchestrator finished in the background, the terminal event was broadcast to an empty handler set — the cache invalidation never fired, the optimistic insert never happened, and `ChatWorkspace`'s return read from a stale messages-query cache.

Fix: lifted the terminal-event cache reconciliation into a new root-level bridge, `useAssistantMessageBridge`, mounted in `RealtimeBridge` next to `useUserMessageBridge`. Symmetric with the user-row bridge — same `setQueryData` splice + `invalidateQueries` pattern. `useAnalysisStream` now only owns the in-flight streaming state (Zustand store updates); the bridges own what's persisted. `npm run lint`, `tsc --noEmit`, and `next build` are clean for the touched files (pre-existing lint warnings on `(auth)/layout.tsx` and `use-upload-document.ts` are unrelated).

## Recent fix: assistant bubble flash + row stranded in unfetched page

After the navigation-survival fix above, the streamed bubble still disappeared for a brief tick when `analysis.done` arrived — only to reappear moments later once the messages query refetch resolved. Two compounding causes:

1. **Optimistic insert was placed in the wrong page.** Both bridges (`useUserMessageBridge`, `useAssistantMessageBridge`) appended new rows to the LAST page of the messages infinite-query cache. But the chat workspace fetches in `order=desc, limit=20`, so newest items live at the START of the FIRST page. Appending to a full last page pushed the row into a logical "page 2" that `hasNextPage` thought existed (because `total` was bumped) but no one ever fetched — the row was stranded outside the rendered list. Only a hard refresh (which bypasses the cache) would land it.

2. **The virtual bubble dropped on `done` before the refetch landed.** `ChatWorkspace`'s `streamingBubble` derivation only rendered the virtual bubble for `state.kind === "streaming"`, so the moment `done` flipped the store, the bubble unmounted. The persisted row only re-appeared after the invalidation's refetch resolved — a visible gap.

Fix:
- Both bridges now prepend the optimistic row into `pages[0].items` (start of the first page) since that's where newest items live in the desc-ordered cache.
- `ChatWorkspace` renders the virtual bubble for both `streaming` AND `done`. Stop condition: the canonical assistant row has landed — detected as the LAST assistant message in `messages` having a non-optimistic id AND content matching the store's final text. This uses the last-assistant heuristic to avoid false positives from old assistant rows whose content happens to match.

## Recent fix: streamed reply vanishing when the stream ends (any chat with prior history)

**Symptom:** the assistant's answer disappeared as soon as the stream finished, and only reappeared after a page refresh. Reproduced on every turn after the first.

**Cause 1 — the stop-condition heuristic latched on the wrong row.** `ChatWorkspace` decides when to drop the virtual streaming bubble in favour of the persisted row. It used `lastAssistant.id !== streamId ⇒ canonical row landed`. In any conversation with prior history the most-recent assistant row is an *older* turn whose id naturally differs from the current `streamId`, so that check was true on the very first render of every new stream. The bubble was suppressed for the entire answer and the reply only showed up on the next refetch — i.e. the vanish.

**Cause 2 — `analysis.done` is published BEFORE the row is committed.** `analyse_query_with_conversation` yields the `AnalysisDoneEvent` (which the request handler publishes to Redis/WS) and only afterwards opens a fresh session to run `insert_message(...)` in a transaction. The bridge's immediate `invalidateQueries()` therefore races the commit: when it lost, the refetch returned a history with no assistant row, TanStack replaced the whole page array, and the optimistic insert the bridge had just written was discarded.

**Cause 3 (minor) — inflated `total`.** The optimistic insert bumped `total` by one. On a conversation whose newest page is exactly full this made `getNextPageParam` compute `loadedSoFar (N) < total (N+1)` and request a page that doesn't exist.

Fix:
- `chat-workspace.tsx` now snapshots the ids present in the cache when each stream begins (`preStream`, via the "adjust state during render" pattern) and treats the stream as covered only when the cache holds a row that is either the bridge's optimistic insert (`id === streamId`) or an assistant row whose id is *not* in that pre-stream snapshot. Pre-existing history can no longer suppress the live bubble. The coverage decision is now pure — computed from `(messages, streamId)` — so the sticky `coveredStreamIdRef` / `trackedStreamId` refs are gone.
- `use-assistant-message-bridge.ts` delegates the post-terminal refetch to `reconcileAfterDone()`, which invalidates and then *verifies* a row for this stream actually landed, retrying up to 5 times with a linear backoff (150 ms × attempt). This closes the publish-before-commit race. It's fire-and-forget so a slow backend never blocks the WS fan-out.
- The optimistic insert no longer bumps `total`; the refetch reconciles the real count in the same tick.

Side effect: removing the render-time ref reads also cleared the pre-existing `react-hooks/refs` ESLint **error** on `chat-workspace.tsx`. `tsc --noEmit`, `npm run lint` (0 errors), and `npm run build` are all clean.

## Recent fix: MPS memory leak in embedding pipeline

`get_default_embedding_model()` now caches the loaded `Qwen3EmbeddingModel` for the lifetime of the process (singleton in `app/services/ai/embeddings.py`). Without this, every `embed_chunks_for_document` Celery task and every `/analysis/query` FastAPI request constructed a fresh `SentenceTransformer`, loading ~1.2 GB onto MPS each time. PyTorch's MPS caching allocator retains freed blocks across GCs, so the pool grew unbounded and eventually tripped `MPS_HIGH_WATERMARK_RATIO` after a handful of requests — exactly matching the "works a few times after restart, then OOMs" symptom. Reusing one instance keeps the allocation flat for the lifetime of the worker / API process. A `reset_embedding_model_singleton()` helper was added for tests, and the autouse `_reset_settings_cache` fixture in `tests/conftest.py` was extended to call it between tests.
